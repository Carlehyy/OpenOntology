# 超级助手 · 消息通知弹窗 UX 评审与优化建议

- **评审对象**：超级助手工作台 → 侧栏「消息通知」弹窗（`NotificationsDialog`）
  - 线上入口：`https://64.83.14.139:8443/#/super-assistant`（admin 账号侧栏可见）
  - 组件源码：`frontend/src/pages/super-assistant/components/NotificationsDialog.tsx`（约 1981 行）
  - 格式化与文案辅助：`frontend/src/pages/super-assistant/components/notificationsFormat.ts`
  - 外壳：`DialogShell`（`AssistantConfiguration.tsx:39-83`），尺寸 `wide` = `w-[min(96vw,64rem)]`
- **评审方式**：真实环境操作（1440×900 亮/暗两态、390px 窄屏、toast、确认弹窗、转发面板、四分区全量走查），结合源码逐行比对与 `DESIGN.md`/`tokens.css` 基线核对
- **评审日期**：2026-10-12（分支 `nano-ontoprompt`）
- **总体结论**：信息架构与工程基础扎实（四分区、键盘漫游、Esc 分层回退、空态引导、确认弹窗语义分级），但**视觉呈现未达同一水准**——尺寸/留白/层级偏弱，且存在两处会直接造成数据丢失或布局破坏的交互缺陷。以下问题按优先级分四档共 33 条。

---

## P0 · 阻断性缺陷（2 条，商业化前必修）

### 1. 桌面端布局模式冲突：外层 `flex-col` + 内层 `md:flex-row`，宽屏下纵向堆叠

**现状（实测 1440px 宽）**：消息分区被压成上下两栏，列表列只有 ~208px 宽，消息标题在第 2 个字后被截断；列表与详情左边界错位 93px；滚动方向变成整页上下滚，与 e2e 固化的「左列表右详情」心智完全不符。390px 窄屏（e2e 用例覆盖的形态）反而是正常的。

**根因**：容器同时挂了 `flex flex-col md:flex-row`（分层断点）与 `h-full`（要求内部撑满），两个约束互斥。断点未生效时 `flex-col` 兜底生效，叠加 `h-full` 引发列宽塌陷与外层滚动。

**建议**：容器去 `flex-col` 改单断点 `md:flex-row`（窄屏单栏已由列表/详情互斥显隐逻辑保证，无需容器再变轴）；修复后跑 `super_assistant_workbench.spec.ts` 补一条 ≥1280px 桌面断言，防止回归。

### 2. 误触遮罩即关弹窗，表单草稿与浏览位置全部丢失

**现状（实测）**：点击遮罩 → Radix 直接关闭 → 发送分区的标题/正文/渠道勾选全部清空，列表滚动位置与选中消息重置（再次打开回「未读」tab）。写了一半的长 Markdown 正文没有任何挽留。

**建议**（三选一，推荐 3）：
1. 关闭前检测「有未发送草稿」→ 弹挽留确认（`ConfirmDialog`，warning 档）；
2. `onInteractOutside` / `onPointerDownOutside` 改为仅 Esc / 关闭按钮可关（工作台型弹窗常见做法，改法最小）；
3. 短期最简：`onInteractOutside={e => e.preventDefault()}`，并在关闭重置逻辑里保留草稿直到发送成功。

## P1 · 结构与布局（6 条）

### 3. 弹窗 71% 视口宽 + 15px 上下边距 + 垂直偏上，观感「铺满全屏」

宽 71% 视口没问题，问题是上下几乎贴边（上 15px、下 15px）、水平居中但垂直偏上约 20px，遮罩露出极少，用户失去「这是浮层」的心理暗示。
**建议**：宽维持 64rem 上限不变；高改 `h-[min(78dvh,42rem)]` 留出呼吸边距（≥40px），并确认垂直居中；`wide` 档圆角从 12px 提到 `--radius-xl`（16px），与平台 `Modal.tsx` 的 `rounded-2xl` 基准对齐。

### 4. 左侧导航与右侧内容之间缺少分隔

四分区导航是纯文字（14px lucide 图标 + 文字），选中态只有品牌浅底色块，与内容区之间无分隔线。
**建议**：加 `border-r border-[var(--color-border)]`；选中态补 `font-medium text-brand-ink`（平台既有选中态语言）。

### 5. 头部与内容区无分隔线、底部无收束

头部（图标盒 36px + 标题 15px + 描述 12px）下方直接铺内容，密度突兀；弹窗无 footer，滚动到底内容贴着圆角边。
**建议**：头部下加 `border-b`（`DialogShell` 已有分隔线变体，本弹窗未用上）；内容区底部统一 `pb-6`。

### 6. 空态占位过高，焦点不聚焦

「没有未读消息」空态垂直居中于 ~510px 高的列里，图标 28px、标题 14px、描述 12px、按钮依次堆叠，间距松散，扫视动线长。
**建议**：图标 32px + 标题/描述提一档（15px/13px），整体间距收紧约 1/3，保持居中但视觉重心更集中。

### 7. 头部描述文案过长且术语化

「消息中转站：多入口接收，站内查看处置，按配置的渠道自动或手动转发」32 字塞在一行，12px 灰字在 71% 宽头部里显得稀薄；「消息中转站」是内部概念，首次使用者无感知。
**建议**：缩短为「接收、处理并转发平台与外部系统的消息」；或保留现文案但限宽两行。

### 8. `flex-1` 与 `min-w-0` 缺失加剧塌陷

列表列 `md:w-[22rem]` 固定宽 + 详情列 `flex-1` 但无 `min-w-0`，Markdown 表格/长 URL 会把详情列撑出滚动条。
**建议**：详情列补 `min-w-0 overflow-hidden`，内部滚动交给正文容器。

## P2 · 视觉细节（12 条）

### 9. 焦点环色值陈旧，违反 §4.4 唯一规格

全部输入框/按钮用 `focus-visible:ring-2 focus-visible:ring-ring`，但 `--ring` 亮色仍是旧绿 `#059669`，主色已是 `#10b981` 系（`--color-primary`）。焦点环与主色打架。
**建议**：核对 `tokens.css` 中 `--ring` 与 `--color-primary` 是否应统一；本弹窗内焦点环只允许 `ring-2 ring-ring` 一档，不要加透明度修饰符（§8 禁止项）。

### 10. 图标尺寸梯度混乱：10/12/13/14/15/16/18 七档

列表预览附件图标 10px、星标 12px、返回/转发/全部已读 13px、附件 14px、详情操作 15px、空态 16px、头部 18px。10px 的回形针在 13px 文字旁几乎不可见。
**建议**：收敛到 12（内联装饰）/ 15（独立操作）/ 18（头部与空态）三档；正文内联图标用 `0.85em` 相对字号。

### 11. 正文与元信息对比度不足（亮暗两态都超线）

正文 13px 灰、元信息 12px 更浅的灰，实测对比度 3.5-4.2:1，低于 WCAG AA 4.5:1；暗色模式下头部描述、元信息、统计标签同样超线。视口全灰的页面里，最该被阅读的正文反而最弱。
**建议**：正文提到 `--color-text-primary` 或加深 secondary；元信息至少 4.5:1。发版前过一遍浏览器 devtools 的对比度检查（重点：`text-secondary` 在 popover 底色上的实际比值）。

### 12. 消息列表预览文本是拼接坨，未按 Markdown 结构降级

实测预览：「库存告警 商品： SKF-6204 轴承 当前库存： 12 件（安全线 50） 库位： A-07 > 本消息由第三方系…」——标题、列表项、引用符 `>` 全部拍平成一行，中英文间无空格。
**建议**：`bodyPreview` 生成时按块级元素降级（标题→加粗行、列表→`·` 分隔），至少过滤引用/表格符号；中英文之间补空格。
**处置（2026-10-13，13f08278）**：经二次审查修正根因后落地——服务端 `bodyPreview` 保留原始换行截断（不再拍平），客户端既有 `stripMarkdownPreview` 行首锚定剥离随即生效；后续对抗审查又补齐未闭合围栏/孤立反引号补齐与结尾孤立语法标点清理。

### 13. 时间显示全是绝对时间戳，无相对时间

列表与详情都是 `2026-10-11 22:35`。通知类产品用户第一关心「多久之前」。
**建议**：≤24h 用相对时间（`3 小时前`），hover `title` 显示完整时间（收件箱弹层已是 `<time>` + title 的做法，直接复用）。

### 14. 详情区五个纯图标按钮辨识度低

星标/归档/转发/标未读/删除五枚 15px 灰图标排排坐，依赖原生 `title` 悬停提示（约 1s 延迟且不可样式化），删除仅 hover 变红。
**建议**：换 ReUI `Tooltip`（无障碍名已有，成本极低）；删除按钮常态给 `text-[var(--color-danger)]`；考虑给「转发」加文字按钮形态（低频高价值操作）。

### 15. 优先级仅靠 6px 圆点，信息密度不足

列表里优先级 = 6px 小圆点，颜色是唯一信号（色弱不可辨、扫描时不可见）；详情里才有「高优」chip。
**建议**：urgent 消息在列表项加左缘 2px 色条或行内小 chip（复用详情的 chip 样式），让「紧急」在列表层就可见。

### 16. 未读列表项品牌色背景过重

`color-mix(accent-soft 55%)` 合成的未读底色实测偏重，且右侧详情区无对应未读提示。
**建议**：降到 25-35%，或改为左侧 2px 品牌色条 + 标题加粗（与 DESIGN.md「浅底深字优先」的纪律一致）。

### 17. 统计概览卡信息层级弱

四卡 24px 数值 + 12px 标签，卡片内边距 12px 偏紧，四卡留白均质没有重点；「转发成功率 50%」这类差值信号无任何颜色语义。
**建议**：数值 28px `tabular-nums`（§3 排版规则：数字密集用等宽）；成功率 <80% 给 warning 色；卡片 padding 提到 16px。

### 18. 「全部已读」纯图标按钮 + 原生 title

仅 13px 信封开启图标，可发现性差；未读为 0 时禁用但无解释。
**建议**：带文字「全部已读」次级按钮（列表头右上），或在 tooltip 说明「将 N 条未读标为已读」。

### 19. 渠道配置区错误信息直接透出后端原文

实测：「投递失败 2026-10-11 22:53：渠道投递失败（notify 返回失败）」——「投递失败」出现两次，`notify 返回失败` 是内部术语。
**建议**：错误行去重 + 映射为可行动文案（「投递失败 · 查看渠道配置检查收件人/API Key」），保留 `lastError` 原文进 tooltip/详情。

### 20. 签发密钥的明文一次性展示条风险高

明文密钥展示无遮挡、无倒计时提醒，「复制」按钮无二次确认路径；关闭弹窗即清空明文（正确），但用户可能没意识到。
**建议**：明文默认打码 + 显式「显示」toggle；展示条加倒计时或强提示「关闭后将无法再次查看」。

### 21. 概览卡空值 `—` 与脚注排版散

「今日入站 —」与脚注「仅计正式投递单，不含渠道测试直发」12px 灰字贴卡底，视觉上像数据缺失。
**建议**：空值用 `0` + 灰色（今日入站为 0 是事实而非未知），脚注移到卡片组下方统一一行。

## P3 · 交互与文案（13 条）

### 22. 首屏未读空态引导按钮文案与信息密度

「查看全部 4 条消息」是唯一 CTA，样式为次级按钮，引导力弱。
**建议**：提为主按钮样式；文案简化「查看全部消息」（数量变化时按钮文案跟着变是噪音）。

### 23. 筛选 tab 无计数

只有「未读」隐含在空态里，其余 tab（已标记/已归档/全部）无数量，用户需逐个点击才知道分布。
**建议**：tab 文字带计数徽标（summary API 已返回 unreadCount/starredCount/archivedCount/totalCount，前端目前丢弃了 3 个字段——纯前端改动）。

### 24. 「已标记」「已归档」命名不对称

「已标记」实为星标（starred），与详情区星标图标的映射不直观。
**建议**：改「星标」「已归档」，或统一「已星标/已归档」。

### 25. 详情正文滚动无吸顶

详情头（标题+操作按钮）随内容一起滚走，长 Markdown 滚几屏后想点「星标」要滚回顶部。
**建议**：详情头 `sticky top-0` + 底色渐隐分隔。

### 26. Esc 分层回退逻辑好但不可见

Esc 依次收转发面板→渠道表单→签发表单→窄屏回列表，这个设计很好，但用户无从得知。
**建议**：弹窗 footer 或帮助 affordance 一行「Esc 逐层返回」；至少在面板展开时给视觉暗示。

### 27. 长列表无日期分组、无置顶逻辑

30 条一页的平铺列表，跨天消息没有「今天/昨天/更早」分组条。
**建议**：按天插入分组标签（数据已有 createdAt）。

### 28. 「转发（0）」计数语义误导

渠道全未勾选时按钮显示「转发（0）」，看起来像「0 条转发成功」。
**建议**：禁用态文案改「选择渠道后转发」，勾选后「转发（2 个渠道）」。

### 29. 渠道 chips 交互暗示弱

「默认全选，点击可增减」12px 说明文字，chips 本身无 checkbox 视觉。
**建议**：chips 内加 checkmark（选中时）+ 边框加强。

### 30. 密钥名称与来源系统混排

密钥列表项「11111ob_notif_cd1727_…」——密钥名（11111）与 key 前缀直接相连展示，难读。
**建议**：名称独立一行加粗，密钥掩码独立一行等宽字体（`--font-mono`）。

### 31. 收件箱 vs 消息通知双通知体系并存

全局顶栏「收件箱」（任务告警）与本弹窗（消息总线）是两套独立体系，普通用户会困惑「通知到底看哪」。
**建议**：至少统一入口徽章逻辑与视觉语言（两者目前 15s 轮询与 99+ 徽章已对齐，做得好）；中长期考虑收件箱并入本弹窗作为一个分区。

### 32. 暗色模式头部描述对比度与收件箱不一致

暗色下本弹窗描述文字对比度低于顶栏收件箱弹层的同类文字。
**建议**：对齐 `--color-text-secondary` 暗色值在两处的实际渲染（可能是 color-mix 合成色在暗色下衰减更深）。

### 33. 无移动端「加载更多」触底加载

30 条分页靠手动点「加载更多」按钮，窄屏下按钮在长列表底部不显眼。
**建议**：改 IntersectionObserver 触底自动加载，按钮保留为兜底。
